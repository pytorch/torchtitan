## Launch

After building or selecting the immutable runtime:

```bash
fb/fair_coreweave/reproduce_aditya_1162984.sh --runtime-id RUNTIME_ID
```

The launcher syncs this checkout, installs the pinned Grain-only compatibility
overlay without modifying the immutable runtime, validates the request with
Slurm, and submits the exact 22-step v11 recipe. Use `--dry-run` to inspect the
rendered batch script or `--no-sync` to reuse an already synchronized tree.

The exact 16-GPU proxy completed successfully as CoreWeave job `1250702`, with
full-step CUDA graphs, gradient accumulation 16, and 26 DistMoE backward
accumulations fused into their producers.

EP64 is a 16-node scale-up group on this four-GPU-per-node cluster. It must use
`--segment 16`; this is a correctness constraint, not only a scheduling hint.
Jobs `1251355` and `1252905` used 8-node segments and failed in DistMoE's first
remote routing-metadata gather because each EP group crossed two NVLink blocks.
Job `1253103` placed the same EP64 group in one 16-node block, passed that
routing operation, and reached a later fused-MLA allocation before exhausting
HBM at DP64. The 265.49 GiB allocation is the expected capacity limit of the
smaller dense-sharding degree, rather than an EP64 routing failure.

Job `1256339` then completed a 10-step 16B DP64/EP64 run in one 16-node block.
It exercised the complete captured forward, backward, optimizer, in-graph GA16,
and deferred-FSDP path. Steps 3 through 9 sustained 44,079-44,969 tokens/s,
with identical loss and gradient norm on every rank. This confirms the EP64
runtime path independently of the 671B model's DP64 capacity limit.

The exact 64-node, DP256, EP64 reproduction is CoreWeave job `1253106`. It
requests four 16-node blocks and uses the reference 22-step profiler schedule.
Its Slurm time limit is 20 minutes; the reference job completed in 14 minutes
57 seconds.

A 32-GPU full-model preflight ran as CoreWeave job `1251400`. It built the
671,026,404,352-parameter model, entered training, and reproduced the reference
graph rewrite counts of 367 scaled-GEMM WGrad fusions and 58 DistMoE backward
fusions. It then exhausted HBM during the first CUDA-graph execution with
265.01 GiB allocated per GPU. This is the expected capacity limit from running
the 671B model with DP32 rather than the target DP256; it is graph-construction
evidence, not a throughput result.

## Local four-GB300 validation

The local runner uses the 16B model as a capacity proxy while retaining the
reference execution path: FSDP4, EP4, TP1, CP1, PP1, sequence length 4096,
local batch size 1, gradient accumulation 16, AOT-FX without Inductor,
full-step CUDA graphs, deferred FSDP synchronization, symmetric-memory buckets,
and BF16 optimizer states.

Copy the sealed runtime archive and its manifest into this layout. The native
runtime is intentionally kept outside the repository:

```text
~/tmp/coda-gt-local-runtime-gb300/
|-- 593b9310487595c6.tar.gz
`-- RUNTIME_MANIFEST.json
```

Prepare it without rewriting the immutable conda prefix:

```bash
fb/fair_coreweave/prepare_aditya_local_runtime.sh
```

The preparation script verifies these checksums before extracting the archive:

```text

bd6172f58eb609f2f6b77064c07faf35e711e1aa1272d7162e46bae6b7f54c8d  RUNTIME_MANIFEST.json
```

It installs the pinned Grain-only dependencies into a separate overlay and
does not run `conda-unpack`. On hosts whose system glibc is older than the
runtime requirement, the runner uses the platform010 loader and the runtime's
CUDA 13.1 compatibility libraries directly.

Validate the runtime and launch the two measurement modes:

```bash
fb/fair_coreweave/run_aditya_local_4gpu.sh --preflight-only
fb/fair_coreweave/run_aditya_local_4gpu.sh
fb/fair_coreweave/run_aditya_local_4gpu.sh --deterministic --tensorboard
```

The runner records the source revision, runtime identity, manifest hash, and
fully quoted command under `~/tmp/coda-gt-local-runs/RUN_NAME/manifest.txt`.
Use at least ten steps for performance measurements and steps 3 through 10 as
the steady-state window.

MXFP8 has no agreed hardware-peak denominator, so TorchTitan correctly reports
MFU as `N/A`. For orientation only, dividing model TFLOP/s by the GB300 BF16
peak of 2,500 TFLOP/s gives 27.95% for fbsource and 27.13% for standalone in
the performance runs. This is a BF16-equivalent utilization proxy, not MFU.

The standalone performance result is currently 2.96% below fbsource. Both runs
produced 136 scaled-GEMM WGrad fusions, 28 all-gather and 29 reduce-scatter
symmetric-memory buckets, and released 31 slabs after clean 10-step training.

The full performance configurations are not bitwise equal. The first optimizer
step's 64 rank-local input, label, and position batches have matching SHA-256
hashes, and eager FSDP4/EP4 forward/backward, minimal FX, the normal pass
pipeline, and repeated GA16 tracing all produce the same result in both trees.
The difference is isolated to the old fbsource `[B, L, D]` graph when deferred
WGrad producer fusion, symmetric-memory FSDP, and CUDA graph capture are all
enabled. Disabling any one produces the standalone step-one result exactly:
loss `11.979890823364258` and gradient norm `8.619784355163574`. Reproducing
fbsource's original loss trajectory would retain that legacy shape-specific
interaction rather than restore a missing standalone feature.
