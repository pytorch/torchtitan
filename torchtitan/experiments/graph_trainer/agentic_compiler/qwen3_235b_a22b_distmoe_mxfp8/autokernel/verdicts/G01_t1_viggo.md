## 2. Reference dispatch and the dw reduction order

`ref_dispatch.py` (`logs/ref_dispatch.log`) profiles reference.py. On device it reports cc (10, 3), 152 SMs,
`get_sm_count(128)` = 2432 and `RmsNormBwdConfig(128 threads, 16 threads/row, cluster 1, no TMA, 2 stages)`.
Profiled kernels: `RMSNormBackward` with grid 2432 x 128 threads for both k (8.6 us) and q (74.5 us), and
`reduce_rows` with grid 32 x 256 threads for each.

**Order derived from the code.** The sources are torch/_native/ops/norm/norms.py, rmsnorm_impl.py and
rmsnorm_kernels.py, torch/_vendor/quack/rmsnorm.py and reduction_base.py, and torch/_native/cutedsl/reduce.py. sm_103
is not in the ((9,0),(10,0)) launch table, so blocks = `min(M, get_sm_count)` = 2432 for both q and k. For a row
`tok * nh + h`:
- tile t = row // 8, slot r = row % 8;
- CTA b = t % 2432 accumulates `acc[b][r] = fma(xh, d, acc)` over increasing t, starting from +0;
- the partial is P[b] = ((acc0 + acc1) + ...) + acc7;
- `reduce_rows(P, 4, 256)`: 64 chains u, each 0 + P[u] + P[u + 64] + ... over 38 rows, then a butterfly over u^1,
  u^2, u^4, then the 8 warp groups summed in order, then bf16.

This confirms the writer's 2432 blocks, config, `reduce_rows(partial, 4, 256)` and the q and k ownership formulas.

`dw_probe.py kernel.py --alts` (`logs/dw_probe.log`):
- **Exact-cancellation probes.** 12 cases x (q, k) x 128 columns. Each column holds 3-5 exactly representable
  terms (+-2^(24+e), +-{1,3}*2^e). They are placed to target one level each: same accumulator chain, rows within
  P[b], the E/O boundary, reduce chain, butterfly, warp groups, or mixed. 6 of the cases add a dense background
  of +-2^-4 products (density 2% or 30%).
  - My numpy-float32 emulator of the order above equals the reference bit for bit on 24/24 (case, kind)
    pairs.
  - 13 alternative orders each differ from the reference on 105-912 columns: chain reversed; P rows reversed, E/O
    split, E+tree(O) and tree; reduce chain reversed; butterfly 4-2-1; groups reversed and tree; blocks 608 (the
    sm_100 launch-table count), 1216 and 4864; and a 30B-style q ownership (32-token blocks of class T % 19).
  - Candidate EXACT on all.
- **Inexact-product probes.** 4 cases x (q, k) x 128 columns. Each column uses two rows of one accumulator chain
  (k: CTAs b < 1664, which have 2 tiles). The values come from exact Fraction arithmetic:
  - On all 128/128 columns of both kinds, the reference equals the FMA forward-order prediction.
  - The reverse-order prediction matches 0/64 columns, and the mul+add prediction matches 0/64.
  - So the reference uses an FMA chain in tile order, which is also the only way the 2-tile k chain order can be
    seen.
  - Candidate EXACT.

## 7. Concurrency and co-residency (`occupy.py`, `logs/occupy.log`; every spinner has a timeout)

The q exchange stays inside the 19 CTAs of one 8-head group: the slot index uses the CTA's hg8, and partners
differ only in the half-block class. So K1 needs one group of 19 CTAs co-resident, not all 152.

The occupier is a kernel whose CTAs use 200 KB of shared memory, so an SM running one cannot also run a K1 CTA
(229.7 KB smem, 168 regs x 384 threads).

**O1: occupier holds N SMs for 20 ms, then the call.**
- N = 1..133: the call finishes in 0.3-1 ms while the occupier still holds its SMs.
- N = 134, 140, 151 and 152: the call waits until the occupier exits (about 22 ms).
- 300 occupier CTAs (two waves): the call waits for both waves.
- EXACT in every case.
- The threshold of 133/134 matches "19 free SMs" under in-order block dispatch.

**O2 (call first, then the occupier) and O3 (graph with a forked occupier branch, 5 replays):** EXACT.

**O4: hazard demo.** The occupier holds N SMs and waits for a flag (300 ms timeout). Then the call runs, and a
setter on a third stream sets the flag.
- N <= 133: the setter runs and the occupier leaves via the flag.
- N >= 134: the setter is never scheduled until the occupier times out. This holds even for a 32-thread setter,
  which would fit next to an occupier CTA, so the dispatcher does not let later grids pass K1's pending CTAs.
  Without the timeout this would be a deadlock.
- reference.py completes in all of these cases.

**Two calls concurrently on two streams** (documented by the writer as unsupported) can **hang**, not only
corrupt (`logs/concurrent_hang_note.txt`, `concurrent_demo.py`).
- It hung twice: once inside a 20-pair loop (py-spy shows it stuck in `synchronize`, GPU at 100%), and once after
  55 EXACT pairs in a 300-pair run (killed by `timeout 45`).
- Cause: each K1 CTA reads the device epoch when it starts. If the other call's K2 increments the epoch while some
  CTAs of this K1 are still undispatched, CTAs of the same call poll for a tag that is never written. `poll_tag`
  has no timeout.
- Pairs that completed were EXACT, because they ran serialized.

## 9. Findings and conditions for the coordinator and the writer

1. **Safe in this training run's pattern.**
   - There is a single compute stream and a full-step CUDA graph.
   - Consecutive G01 calls are stream-ordered (and data dependent), so call n's K2 has finished before call n+1's
     K1 reads the epoch.
   - Collectives and other kernels on side streams can only delay the call. A hang needs at least 134 of the 152
     SMs held by kernels that wait for later work, and NCCL / Dist-MoE comm kernels use far fewer SMs.
2. **Not safe.**
   - Two calls in flight on two streams at the same time. This can hang the GPU. For example, a future
     EP-overlap or chunked schedule that runs two attention-backward regions in parallel at these exact shapes.
   - SM partitions (MPS, green contexts) of fewer than 19 SMs.
   - The writer's HANDOFF says "must not run concurrently", but the consequence is a hang, and that should be
     documented as such. A bounded `poll_tag`, or reading a per-call tag that cannot change during a call, would
     make the failure explicit instead of a hang.
3. **Device assumptions.**
   - Import asserts 152 SMs on the current device.
   - Import allocates the unit tables, the 8 MB xbuf and the epoch on the current device. Other devices are set up
     lazily, so a first call on another device inside graph capture would allocate and do a pageable H2D upload
     during capture (same as t30).
   - No device index is hard-coded. Per the brief, only cuda:0 was tested.
4. **Upstream dependency.** Like t30, this kernel depends on quack's reduction order. It reproduces the order of
   the vendored quack RMSNorm backward on sm_103 with 152 SMs (2432 blocks). A torch or quack update that changes
   the block count or the launch table (for example adding sm_103 to the table, which gives 608 blocks) breaks dw
   parity. The emulator alternative "blocks 608" differs on 912 probe columns.
5. **No PDL.** The source has no griddepcontrol or programmatic or cooperative launch.
