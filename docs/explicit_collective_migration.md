# Explicit collective migration

This document inventories communication currently generated by
`ShardingConfig` source-to-destination redistribution and proposes follow-up
work to make those collectives explicit at their semantic owners.

The audit uses merged PR #4704 on `main` at `9e159aed7`. That PR already moves
the standard tensor-parallel projection
collectives into `ColumnParallelLinear`, `RowParallelLinear`, or the enclosing
module when several projections share one input.

## Redistribution semantics

`Module._redistribute_inputs()` and `Module._redistribute_outputs()` call
`spmd_redistribute_per_axis()`. For each non-singleton mesh axis, the relevant
source-to-destination transitions have the following autograd behavior:

| Transition | Forward | Backward |
| --- | --- | --- |
| `P -> S(d)` | reduce-scatter | all-gather |
| `P -> I` | all-reduce | no communication |
| `P -> R` | all-reduce | all-reduce |
| `S(d) -> R` | all-gather | reduce-scatter |
| `I -> R` | no communication | all-reduce |
| `I -> S(d)` | local shard | all-gather |

`R -> S(d)`, `R -> I`, and `S(d) -> P` do not communicate. They may still be
useful semantic transitions, but they are not part of the collective migration.

No declarative `S(i) -> S(j)` transition was found, so this mechanism currently
inserts no all-to-all. Expert token-dispatch all-to-alls are already explicit
and are outside this audit.

## Migration inventory after PR #4704

Checked items have been converted in the local Core MoE work that follows the
cherry-pick. Unchecked items still use generic source-to-destination
redistribution.

- [ ] Token embedding output in
  `torchtitan/models/common/decoder_sharding.py`:
  - SP: `P -> S(0)`, forward reduce-scatter and backward all-gather.
  - No SP: `P -> I`, forward all-reduce.
- [ ] Final decoder norm output in
  `torchtitan/models/common/decoder_sharding.py`:
  - SP: `S(0) -> R`, forward all-gather and backward reduce-scatter.
  - No SP: `I -> R`, forward no-op and backward all-reduce.
- [ ] DeepSeek V3 MTP repeats the final-norm transition for every MTP layer in
  `torchtitan/models/deepseek_v3/sharding.py`.

### MoE boundaries

The conditional transitions below are defined in
`torchtitan/models/common/moe_sharding.py`.

- MoE input transitions declared with EP disabled cannot communicate in a
  supported configuration: MoE enforces `EP >= TP`, so `EP=1` implies `TP=1`.
- [x] MoE output with EP enabled and SP disabled uses `P -> I`, an all-reduce
  in forward.
- [x] Router input with EP enabled and SP disabled uses `I -> S(0)`. Its
  forward is a local shard, but its input-gradient path contains an all-gather.
- [x] RoutedExperts input with EP enabled and SP disabled also uses
  `I -> S(0)` and therefore has a backward all-gather.
- [x] Qwen3.5's sigmoid-gated shared expert keeps a parent-owned input
  transition because `w13` and `gate` share the input:
  - EP plus SP: `S(0) -> R`, forward all-gather and backward reduce-scatter.
  - EP without SP: `I -> R`, backward all-reduce.
- [x] Kimi K3 latent MoE replaces the RoutedExperts input transition with the
  equivalent `I -> S(0)` transition on `routed_down`, again producing a
  backward all-gather when EP is enabled without SP.
- [ ] Shared-expert `w2` remains a plain `Linear` in the current PR #4704 and
  uses generic `P -> S(0)` redistribution when EP and SP are enabled.

### Multimodal decoder boundaries

- [ ] Qwen3.5, Kimi K2.5, and Kimi K3 keep token embedding outputs replicated
  for vision scatter. Their `P -> R` transition performs an all-reduce in both
  forward and backward.
- The subsequent first-layer `R -> S(0)` transition is a local shard and does
  not insert a collective.

### Vision TP boundaries

The common vision path keeps activations invariant across TP. Its remaining
`I -> R` transitions are forward no-ops that insert all-reduces in backward:

- [ ] The `VisionAttention` parent input shared by Q, K, and V.
- [ ] `VisionMLP.fc1`.
- [ ] The first projection in the Qwen3.5 merger and Kimi MoonViT projector.
- [ ] Qwen3.5 and MoonViT encoder output, before the decoder-side vision
  scatter.
- [ ] Muse Glimmer `perception_emb_norm` output when decoder SP is enabled.

The vision attention projection and MLP output reductions are already explicit
in PR #4704 through `InvariantRowParallelLinear`.

### Flux context parallelism

- [ ] Every executed Flux inner-attention call independently changes K and V
  from `S(1)@CP -> R@CP`. This inserts two forward all-gathers and two backward
  reduce-scatters per attention invocation. The declarations are in
  `torchtitan/models/flux/sharding.py`.

### Transformers modeling backend experiment

PR #4704 does not convert the projection path in
`torchtitan/experiments/transformers_modeling_backend/hf_sharding.py`. The

- [ ] Embedding output:
  - SP: `P -> S(1)`, reduce-scatter forward and all-gather backward.

- [ ] LM-head input under SP: `S(1) -> R`, all-gather forward and

- [ ] Attention output and dense MLP down projections:

- [x] The HF-adapted Titan MoE root uses the explicit Core MoE input/output
  transitions in
  `torchtitan/experiments/transformers_modeling_backend/moe_replacement.py`.

## Core MoE implementation status

The current PR #4704 keeps common shared-expert `w13` as
`ColumnParallelLinear` and changes `w2` back to plain `Linear`. The former is
correct for supported configurations because `EP >= TP`: whenever a TP group
exists, EP is enabled and the `w13` input is `I` without SP or `S(0)` with SP.
The latter avoids reducing the shared branch early when EP is enabled without
SP. The Core MoE follow-up still needs to make the plain `w2` output reduction
explicit when EP and SP are both enabled.

## Proposed PR sequence

Five follow-up PRs keep ownership and numerical validation reasonably isolated:

1. **Core MoE collectives (in progress locally)**
   - Move MoE entry/exit, router, RoutedExperts, Qwen3.5 shared-gate, and Kimi
     latent-projection transitions to their semantic owners.
   - Test all supported `(EP, SP)` combinations, including backward-only
     collectives and optional padding masks.

2. **Decoder root collectives**
   - Move token-embedding reduction into the embedding implementation.
   - Move the final hidden-state gather to the terminal norm/model boundary.
   - Cover SP and no-SP, chunked loss, tied weights, PP endpoints, and
     DeepSeek V3 MTP.

3. **Vision and multimodal collectives**
   - Add an invariant-input column-parallel boundary or explicit parent-owned
     `I -> R` conversion for vision modules.
   - Move vision-encoder output and multimodal embedding reductions.
   - Cover Qwen3.5, Kimi K2.5, Kimi K3, and Muse Glimmer.

4. **Flux CP collectives**
   - Move the K/V CP all-gathers into the attention implementation.
   - Keep the local SPMD wrapper placement-only.

5. **Transformers modeling backend parity**
   - Convert the experimental HF embedding, attention, dense MLP, output
     projection, LM-head, and adapted MoE boundaries.
   - Keep this separate because its tensors retain a batch dimension and its
     module discovery is dynamic.

This is five follow-up PRs after #4704, with the first now represented by the
local working changes. The first four complete core TorchTitan; the fifth
completes the experimental Transformers backend. If review bandwidth favors
larger changes, PRs 3 and 4 can be combined, but the MoE and HF work should
remain separate.

## Verification requirements

Each PR should include:

- Exact collective-count tests for forward and backward.
- SP-on and SP-off coverage where applicable.
- All supported EP/SP combinations for MoE.
- Bitwise-identical loss and grad norm against the pre-refactor path with
  `--debug.seed=42 --debug.deterministic`.
- At least 10 steps for performance comparisons.
