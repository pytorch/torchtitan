# DSv3 671B: GraphTrainer memory and scheduling on 64 x GB300

**Hardware: 64 x NVIDIA GB300 GPUs.**

Original campaign: fourteen real MAST jobs, twelve completed and verified on all 64 ranks through 17 optimizer updates, plus two all-rank capacity OOM controls. The tables below use actual hardware measurements for successful jobs and explicitly labeled planning projections for OOM jobs.

**Added budget sweep:** two further SAC + CPU activation-offload jobs at BS10/GA8 are scheduled with **60 GiB and 80 GiB** budgets; the original 100 GiB run is the measured reference. [Sweep table](#cpu-activation-offload-budget-sweep).

**GA and offload settings**

| Setting | Value |
| --- | --- |
| GA8 parameter gathering, main progression | All-gather every microbatch; gathered parameter representations are reshared between microbatches. |
| GA8 gradient reduction, main progression | Every microbatch. |
| CPU activation offload budget | `sac_cpuoffload_bs10`: **100 GiB**; new SAC sweep: **60/80 GiB**; `full_recompute_cpuoffload_bs6_det42`: **80 GiB**; offload is disabled in other original runs. |

The per-run gather column distinguishes whole-update retention in `full_recompute_bs6_gather_first` from the legacy forward-only retention with backward regathers. Offload budgets are activation-selection quotas in binary GiB per rank. Pinned allocation and process RSS can exceed the quota.

## 5. Startup cost and precompile potential

**Compilation / graph setup is approximately 2.7-3.2 minutes per completed 64-GPU launch.** The new column reports **161.79-190.15 seconds**, calculated from all 64 ranks for each of the twelve completed original jobs. No matched precompiled launch has been measured; these figures describe the existing startup path.

### What is measured

- **Compilation / graph setup, approximate:** the interval between each rank's recorded `before_step_1` observation and its final `GraphPP compiled ...` log, then the maximum across ranks. It covers initial input preparation, FX forward/loss/backward tracing, normalization, memory-policy and rematerialization passes, FSDP scheduling/bucketing, construction of GA8 action graphs and regional Inductor compilation. The observation precedes the train-step timer by telemetry overhead, so this is an approximate startup interval rather than an isolated compiler measurement.
- **Logged compiler graph passes:** summing the top-level `All N graph passes took ...` durations per rank gives **84.84-106.18 seconds**, then taking the maximum across ranks. This includes pass bookkeeping and graph inspection; it excludes FX tracing and time between pass batches. It is included in the broader startup column and must not be added to it.
- **First-update excess:** maximum-rank update-1 duration minus the mean maximum-rank duration of timed updates 6-15 is **265.83-309.49 seconds**. This includes graph preparation plus first execution, runtime initialization and other warmup work. It must not be labeled entirely as compilation time.
- **Five-update warmup excess:** `sum(update_times_1_to_5) - 5 * steady_update_time` is **303.29-348.18 seconds**. Initial CUDA graph capture occurs during this warmup; this figure is broader than compilation.
- **HF checkpoint loading:** the maximum rank's explicit checkpoint-loading timer is **540.13-616.99 seconds** (**9.0-10.3 minutes**), before training updates. It is separate from the startup column.

For example, **Full BS10** spends **167.43 s** reaching its compiled GA8 graphs. Update 1 takes **349.61 s**, versus **67.89 s/update** in steady state, giving **281.72 s of first-update excess**. Update 2 takes **100.77 s**, with another **32.88 s of excess** during runtime warmup/capture. Checkpoint loading takes **540.13 s** separately. Subtracting all first-update excess as a precompile saving would overstate the identified graph-preparation target.

### What a reusable precompiled artifact would move out of training startup

The intended precompile path performs FX tracing, graph transformations and Inductor compilation once, saves the graph and compiled regions, and loads the artifact on training ranks. With complete artifact coverage of the report's GA8 schedule, **roughly 160-190 seconds per 64-GPU launch is the current graph-preparation target**, before artifact distribution, deserialization and runtime binding costs. The measured interval includes initial input preparation, which still has to execute, so it is a proxy for the target rather than a guaranteed removable duration. At a 64-GPU allocation, this interval corresponds to approximately **2.9-3.4 GPU-hours of allocated time per launch**; this is potential accounting, not a measured precompile speedup.

The compilation work moves to the artifact-generation phase and can be reused for subsequent matching launches/restarts. Training still needs model initialization, distributed communicator and runtime setup, HF checkpoint loading, first-use work in native/custom kernels, and CUDA graph capture on the actual GPUs. Artifact loading also has a cost. Precompile does not remove the separate 9-10 minute checkpoint-loading phase or automatically turn the first update into a steady-state update.

### Current GA8 implementation scope

The current [precompile entry point](https://github.com/pytorch/torchtitan/blob/gt-ptc-runs-candidate-1310/torchtitan/experiments/graph_trainer/precompile_main.py) serializes a joint forward/loss/backward graph. The [joint graph loader](https://github.com/pytorch/torchtitan/blob/gt-ptc-runs-candidate-1310/torchtitan/experiments/graph_trainer/spmd_graph_builder.py) can load that graph instead of tracing it. However, the [GA scheduler](https://github.com/pytorch/torchtitan/blob/gt-ptc-runs-candidate-1310/torchtitan/experiments/graph_trainer/spmd_gradient_accumulation_graph_builder.py) still extracts, transforms and compiles its scheduled action graphs through `_build_scheduled_fwd_bwd_graphs` / `_compile_scheduled_fwd_bwd_graphs`; those calls do not skip compilation when an artifact directory is set.

Consequently, **setting `compile.precompile_artifact_dir` alone is not qualified evidence that all reported GA8 compilation time disappears**. Saving/loading the final scheduled actions and validating the exact DSv3 + MTP1, MXFP8/native-MoE, GA8 configuration are needed before claiming the full startup reduction. The numbers above are a measured startup baseline and an approximate optimization target. The actual saving needs a matched artifact-backed launch on the same workload and runtime.

Precompiled artifacts must match the model, shapes, parallelism, schedules, compiler options and runtime versions. [Precompile documentation](https://github.com/pytorch/torchtitan/blob/gt-ptc-runs-candidate-1310/torchtitan/experiments/graph_trainer/README.md#pre-compile-compile-on-one-rank) / [artifact representation](https://github.com/pytorch/torchtitan/blob/gt-ptc-runs-candidate-1310/torchtitan/experiments/graph_trainer/precompile.py).

## 6. Measurement and reproduction

- Each successful run has 17 total optimizer updates: warmup 1-5, **ten measured updates 6-15**, compute profile 16 and allocator snapshot 17. Profiling is separate from timing.
- Update duration is the maximum across 64 ranks, averaged over the ten measured updates. Tokens/s/GPU equals global_batch * 4096 / 64 / mean_update_seconds.
- **MFU (%)** is the archived `mxfp8_mfu_percent`: `100 * tokens_per_second_per_gpu * 291853541376 / 5e15`. The archived model-cost estimate is 291.854 billion FLOPs/token; recomputation overhead is excluded. The dense MXFP8 reference is **5 PFLOP/s/GPU**: [NVIDIA Blackwell Ultra datasheet](https://dam-cdn.nvd.orangelogic.com/AssetLink/1k0p832eq8r5ca0u5383ie5o4tp3bst1.pdf), page 5, individual GB300 FP8/FP6 10 PFLOP/s sparse, with footnote 2 specifying dense as half. The archived reference PDF SHA256 is `ccdffc064731cc160016f4c7a77ecfa37983038bcaf60e39190ba4175b39c7c8`.
- This is model MFU normalized to the MXFP8 reference for mixed MXFP8/BF16/TF32 execution. It is not measured kernel utilization. The archived BF16-equivalent normalization uses 2.5 PFLOP/s and gives twice the displayed percentage. OOM jobs have no completed measured updates, so MFU and throughput are unavailable.
- Memory is the maximum recorded PyTorch allocated/reserved peak across all 64 ranks and updates 1-17, including capture/profiling. CUDA replay's allocated bookkeeping counter does not measure transient replay liveness; use recorded capture peaks and reservation for capacity.
- Each configuration has one hardware trial. Cross-batch throughput does not isolate offload or recomputation overhead. Original nondeterministic capacity rows and strict numerical qualification are separate.
- Nominal offload quotas use binary GiB selection limits. CPU liveness, pinned allocation and RSS are separate measurements; the quota does not cap process RSS.
