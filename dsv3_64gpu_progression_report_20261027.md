# DSv3 671B: 64 GPU GraphTrainer memory and scheduling progression

Fourteen real MAST jobs: twelve completed and verified on all 64 ranks through 17 optimizer updates, plus two all-rank capacity OOM controls. The tables below use actual hardware measurements.

## 1. Main progression table

**Fixed:** DeepSeek V3 671B plus one MTP layer, 64 GB300 GPUs, FSDP64/EP64, PP1, sequence 4096, GA8, balanced routing, native MXFP8 Mega, FP32 GPU master weights and standard gradient storage, GPU BF16 Adam moments, scratch factor 1, minimum activation slots and eight loss chunks. Parameter gathering and gradient reduction occur every microbatch; WGrad fusion is disabled for this table.

**Global batch changes with local BS:** BS6 gives 3072 samples/update; BS10 gives 5120. These six runs use compute source `1457497`, Torch `149ae98`, seed 14536 and deterministic algorithms disabled.

Read the progression as: **NoAC BS6 OOM -> SAC BS6 fits -> SAC BS10 OOM -> SAC + offload BS10 fits**. Full recomputation provides additional choices at both BS6 and BS10.

At BS10, Full uses 11.86 GiB more reservation than SAC + offload, with 3.30% higher measured throughput. P5 uses a 100 GiB nominal activation-selection quota; its maximum observed pinned allocation is 144.66 GiB/process versus 0.063 GiB for P6. The quota is not a process-memory limit.

P1 fails during the first microbatch of update 1. P4 completes its first microbatch, then fails during the second; neither completes an optimizer update or produces a measured throughput. Both OOMs occur after checkpoint initialization and affect all 64 ranks.

## 3. Matched scheduling flexibility

Full BS6/GA8, global batch 3072, last-microbatch gradient reduction and **WGrad fusion enabled**. Both jobs use the same source `2eb747d`, workspace package `00ebfb80`, Torch `149ae98` and strict seed 42. A comparison of 11022 constructed configuration leaves finds only the parameter-gather cadence difference.

| ID | Policy / schedule | Local BS | Global batch | Outcome | Allocated / reserved peak GiB | Tokens/s/GPU | Seconds/update | MAST job |
|---|---|---:|---:|---|---:|---:|---:|---|
| S1 | Every microbatch gather | 6 | 3072 | PASS, all 64 x 17 | 213.35 / 221.66 | 4,726.74 | 41.5948 | [Job](https://www.internalfb.com/msl/studio/runs/mast/dsv3-night-64g-ep64-b6-gather-every-det42-20261026-ivankobzarev) |
| S2 | First microbatch gather | 6 | 3072 | PASS, all 64 x 17 | 240.74 / 248.53 | 4,827.56 | 40.7262 | [Job](https://www.internalfb.com/msl/studio/runs/mast/dsv3-night-64g-ep64-b6-gather-first-det42-20261026-ivankobzarev) |

First retains required parameter representations across the whole update. Actual rank 0/update 16 traces show **1024 AllGather kernel slices for Every, versus 64 in the first microbatch and zero later for First**. Both show 192 ReduceScatter slices: 16 in each early microbatch and 80 in the last. All ranks have positive applicable fusion records, and the two jobs have exactly equal logged scalars at all 17 updates.

First uses 26.873 GiB more reservation, with 2.09% lower observed update time and 2.13% higher throughput. These are single hardware trials; profile counts do not establish network bytes or a distributed critical path.

## 5. Measurement and reproduction

- Each successful run has 17 total optimizer updates: warmup 1-5, **ten measured updates 6-15**, compute profile 16 and allocator snapshot 17. Profiling is separate from timing.
- Update duration is the maximum across 64 ranks, averaged over the ten measured updates. Tokens/s/GPU equals global_batch * 4096 / 64 / mean_update_seconds.
- Memory is the maximum recorded PyTorch allocated/reserved peak across all 64 ranks and updates 1-17, including capture/profiling. CUDA replay's allocated bookkeeping counter does not measure transient replay liveness; use recorded capture peaks and reservation for capacity.
- Each configuration has one hardware trial. Cross-batch throughput does not isolate offload or recomputation overhead. Original nondeterministic capacity rows and strict numerical qualification are separate.
- Nominal offload quotas use binary GiB selection limits. CPU liveness, pinned allocation and RSS are separate measurements; the quota does not cap process RSS.
