# DSv3 671B: GraphTrainer memory and scheduling on 64 x GB300

**Hardware: 64 x NVIDIA GB300 GPUs.**

Original campaign: fourteen real MAST jobs, twelve completed and verified on all 64 ranks through 17 optimizer updates, plus two all-rank capacity OOM controls. The tables below use actual hardware measurements for successful jobs and explicitly labeled planning projections for OOM jobs.

**Added budget sweep:** two further SAC + CPU activation-offload jobs at BS10/GA8 are scheduled with **60 GiB and 80 GiB** budgets; the original 100 GiB run is the measured reference. [Sweep table](#cpu-activation-offload-budget-sweep).

**GA and offload settings**

| Setting | Value |
| --- | --- |
| GA8 parameter gathering, main progression | All-gather every microbatch; gathered parameter representations are reshared between microbatches. |
| GA8 gradient reduction, main progression | Every microbatch. |
| CPU activation offload budget | `sac_cpuoffload_bs10`: **100 GiB**; new SAC sweep: **60/80 GiB**; `full_recompute_cpuoffload_bs6_det42`: **80 GiB**; offload is disabled in other original runs. |

The per-run gather column distinguishes whole-update retention in `full_recompute_bs6_gather_first` from the legacy forward-only retention with backward regathers. Offload budgets are activation-selection quotas in binary GiB per rank. Pinned allocation and process RSS can exceed the quota.

## 5. Graph preparation and precompile

**GraphTrainer graph preparation takes approximately 112.27-167.59 seconds (1.9-2.8 minutes) per audited 64-GPU launch.** This is startup graph processing before training execution. It is measured from recorded phase boundaries, without subtracting a steady-state update from a warmup iteration. All fourteen original jobs were audited on all 64 ranks, using the same versions/attempts as the performance rows. Twelve finish training; the two OOM controls complete graph preparation before failing during execution, so their preparation times are also available.

### Timing boundaries

For each rank, the interval begins at its **last `preprocess_inputs_end` event in update 1**, after all eight microbatches are ready, and ends at its **final `GraphPP compiled ...` log**. The table reports the maximum of these 64 per-rank durations. This covers FX forward/loss/backward tracing, normalization, memory-policy and rematerialization passes, FSDP extraction/scheduling/bucketing, construction of GA8 action graphs and regional Inductor compilation. Input fetching/preprocessing, checkpoint loading, subsequent forward/backward execution, optimizer updates and CUDA graph capture are outside this interval.

The archived runs have no dedicated `prepare_graphs` entry/exit timer. These are therefore **approximate graph-preparation measurements**: the input-ready boundary can include runtime/input wrapping immediately before tracing, and the final compilation marker precedes the last graph-binding bookkeeping. The earlier 161.79-190.15 s before-update-1 interval included input preparation and is not used in these tables.

For example, **Full recompute BS10** has **~141.77 s** of graph preparation at its slowest rank (45). Summing its logged graph-pass batches gives **88.20 s** at the maximum rank; that narrower sum excludes FX tracing and work between pass batches and is already part of graph preparation. Across the audited jobs, graph-pass batch sums are **63.46-106.18 s**. Neither first-update duration nor cumulative warmup overhead is used as the graph-preparation metric.

Every numeric cell in the new column links to the slowest rank's **structured log**, which records the input-ready timestamp. Its existing **MAST job** link provides the corresponding final compilation marker, and its **Profile 16, rank 0** link remains the steady-state execution profile. [All-rank timing derivation and log checksums](/home/ivankobzarev/tmp/dsv3-64gpu-startup-report-evidence-20261027/graph-preparation-analysis.json).

### What precompile can remove

A reusable artifact covering both the traced joint graph and the final scheduled GA8 action graphs would move tracing, graph transformations, scheduling and compilation to artifact generation. The measured **~112-168 s** graph-preparation interval is the processing budget available to reduce per launch; artifact distribution/loading and runtime binding would still cost time. This is an optimization target, not a measured precompile saving.

The current [precompile entry point](https://github.com/pytorch/torchtitan/blob/gt-ptc-runs-candidate-1310/torchtitan/experiments/graph_trainer/precompile_main.py) saves a joint forward/loss/backward graph, and the [joint graph loader](https://github.com/pytorch/torchtitan/blob/gt-ptc-runs-candidate-1310/torchtitan/experiments/graph_trainer/spmd_graph_builder.py) replaces FX tracing with artifact loading. However, the [GA8 builder](https://github.com/pytorch/torchtitan/blob/gt-ptc-runs-candidate-1310/torchtitan/experiments/graph_trainer/spmd_gradient_accumulation_graph_builder.py) still extracts, transforms and compiles scheduled actions through `_build_scheduled_fwd_bwd_graphs` / `_compile_scheduled_fwd_bwd_graphs`. ## 6. Measurement and reproduction

- Each successful run has 17 total optimizer updates: warmup 1-5, **ten measured updates 6-15**, compute profile 16 and allocator snapshot 17. Profiling is separate from timing.
- Update duration is the maximum across 64 ranks, averaged over the ten measured updates. Tokens/s/GPU equals global_batch * 4096 / 64 / mean_update_seconds.
- **MFU (%)** is the archived `mxfp8_mfu_percent`: `100 * tokens_per_second_per_gpu * 291853541376 / 5e15`. The archived model-cost estimate is 291.854 billion FLOPs/token; recomputation overhead is excluded. The dense MXFP8 reference is **5 PFLOP/s/GPU**: [NVIDIA Blackwell Ultra datasheet](https://dam-cdn.nvd.orangelogic.com/AssetLink/1k0p832eq8r5ca0u5383ie5o4tp3bst1.pdf), page 5, individual GB300 FP8/FP6 10 PFLOP/s sparse, with footnote 2 specifying dense as half. The archived reference PDF SHA256 is `ccdffc064731cc160016f4c7a77ecfa37983038bcaf60e39190ba4175b39c7c8`.
- This is model MFU normalized to the MXFP8 reference for mixed MXFP8/BF16/TF32 execution. It is not measured kernel utilization. The archived BF16-equivalent normalization uses 2.5 PFLOP/s and gives twice the displayed percentage. OOM jobs have no completed measured updates, so MFU and throughput are unavailable.
- Memory is the maximum recorded PyTorch allocated/reserved peak across all 64 ranks and updates 1-17, including capture/profiling. CUDA replay's allocated bookkeeping counter does not measure transient replay liveness; use recorded capture peaks and reservation for capacity.
- Each configuration has one hardware trial. Cross-batch throughput does not isolate offload or recomputation overhead. Original nondeterministic capacity rows and strict numerical qualification are separate.
- Nominal offload quotas use binary GiB selection limits. CPU liveness, pinned allocation and RSS are separate measurements; the quota does not cap process RSS.
